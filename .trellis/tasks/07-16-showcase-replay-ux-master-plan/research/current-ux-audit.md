# Showcase / WorkflowReplay 当前体验审计

日期：2026-07-16
基线：`main@4967acbc`，部署服务 `http://localhost:8889`

## 审计方法

- 使用 CodeGraph 检查 `Showcase.vue`、`WorkflowReplay.vue`、
  `CheckpointRail.vue`、`useWorkflowReplay.ts` 的结构和状态关系。
- 检查当前公开工作流列表、状态和 checkpoint history 的真实响应。
- 在 `1440 × 1100` 与 `390 × 844` 视口下检查 `/` 和一个真实已完成工作流的
  `/replay/:threadId` 页面。
- 对照 2026-07-15 至 2026-07-16 已完成和仍处于 in-progress 的体验任务，区分
  “已具备能力”与“仍需优化问题”。

## 已具备、必须保留的能力

- Showcase 已支持列表优先、详情延迟并发加载、30 秒会话缓存、筛选/排序 URL
  同步、推荐项去重、返回上下文恢复和局部详情重试。
- Replay 已支持 live state / replay selection 分离、有效 checkpoint 默认选择、
  checkpoint 深链、移动端检查点折叠、稳定最终摘要、部分成功和错误状态。
- 两页均为公开路由，支持双语、暗黑模式、reduced-motion 基础降级和匿名交互埋点。
- 当前真实路径 Showcase → Replay → checkpoint → 返回可工作。

## 展示页观察

1. 页面身份仍偏“公开运维工作区”：突出总工作流、运行中、需关注、平均进度，
   但首次访客更需要“产品能带来什么、真实产出是什么、为什么可信”。
2. `390 × 844` 下 Hero 和统计区占据大部分首屏，第一条真实案例只在首屏底部露出，
   案例证据仍不够靠前。
3. Hero 标题使用“工作流实例”，与下方工作流区语义重复；动态统计在数据量仅 3 条时
   反而强化样本少，而非建立信任。
4. 推荐案例虽然已从普通列表去重，但推荐原因、价值证据和唯一主动作仍较弱；
   推荐卡和普通卡的信息密度接近，视觉焦点不够明确。
5. 公开卡片出现内部表达，如 `trend`、`P1`、`viral`、硬编码 `views/likes`，
   对非内部用户不友好，也破坏双语一致性。
6. 多层玻璃、背景网格、星图、树枝、轨道和扫光共同存在，品牌感明显，但浅色模式下
   表面边界与正文对比偏弱，业务证据容易与装饰竞争。
7. Showcase 直接调用未认证的 `/workflow/list` 和 `/workflow/status/:threadId`，
   当前没有显式“允许公开展示”的案例治理层；公开体验与数据边界没有形成产品契约。

## 工作流回放页观察

1. 页面已能在桌面首屏展示结果，但三栏中左栏、右栏和大量 10px 元信息压缩了中心阅读区；
   内容少时又出现大片空白，布局没有随结果密度自适应。
2. `390 × 844` 下顶部身份、阶段导航和检查点入口占据约三分之一首屏；阶段横向滚动
   缺少明确边缘提示，用户不容易知道右侧还有阶段。
3. 49 个 checkpoint 的示例把系统节点与有业务产出的节点放在同一层级；默认用户需要
   理解代理名、step 和数据点，认知成本高。
4. “回放”当前更接近快照检查器：缺少清晰的上一关键步骤/下一关键步骤控制、步骤进度和
   结果阅读连续性。自动播放不是 P0，但顺序浏览能力应是核心。
5. 公开结果可出现原始 `auth_failed`、英文 status、`score_source`、seed、JSON fallback
   等内部技术表达；这会降低可信度，也可能扩大公开信息面。
6. `AgentResultRipple.vue` 在若干字段缺少结构化 presenter 时会 `JSON.stringify`；
   `AgentResultPublish.vue` 和 `AgentResultCreative.vue` 直接展示后端 status。
7. 未登录用户看完公开回放后没有主 CTA；“进入管控台”只对已登录用户渲染，公开转化链路
   在最有说服力的页面中断。
8. `CheckpointRail.vue` 在 `<button>` 上覆盖 `role="listitem"`，会破坏原生按钮语义；
   阶段和 checkpoint 的键盘模型需要统一。
9. 当前 20 条 checkpoint 首包超过 1 MB，30 秒 session cache 只能改善重复打开，
   不能解决首次访问。需要 metadata manifest 与按选中项加载详情的接口/状态模型。
10. 页尾大型“创作轨迹”视觉在结果后占据明显面积，但不能帮助用户完成比较、理解或转化，
    应降级为可选解释层。

## 任务治理观察

当前有 11 个 07-15 Showcase / Replay / 全局视觉任务仍标记为 in-progress。它们多为
局部视觉、层级、节奏和背景迭代，且共享两个超大 route component。实施本总方案前应：

1. 将旧任务标记为本 PRD 的输入或已被替代，不再并行实施。
2. 只保留一个主任务和有限子任务，按 API/基础组件/Showcase/Replay/质量分 PR。
3. 每个 PR 固化截图、状态 fixture 和性能预算，避免“再调一轮视觉”没有完成定义。

## 审计结论

下一阶段不应继续增加装饰或重复修复已完成的状态逻辑。重点应从“功能可用”转向：

- 让 Showcase 成为可信案例与转化页面，而不是公开运维看板。
- 让 Replay 成为面向用户的过程解释与顺序审阅工具，而不是内部 checkpoint 浏览器。
- 建立显式的公开案例/回放数据契约和脱敏层。
- 解决首个 Replay checkpoint payload 过大、关键内容字号过小和公开技术字段泄漏。
- 用单一总 PRD、可拆分 PR、量化指标和状态矩阵收敛后续迭代。
